# 明镜 W0 架构基线验收主表

裁决对象是首条受控执行链路采用的设计基线。需求源为《明镜智能体应用通用工程架构需求说明书》v0.4.1，私有原件 SHA-256 `75ac634a98393b5f99fb28901a6a91bc7431290143b6458bbf1f9a2af5f23062`。依据原件 41 项 FR、11 项 NFR、7 项 TS、17 项 AC，连同第 1、2、4、5.2、6.1、7–9 节及七图的文字和边界。图示的控制、执行、数据与能力、治理观测是逻辑职责。涵盖首期及后续完整产品；示例技术、可选记忆/委派和具体业务不自动列为必选。按编号检索第一列，可追到当行检验。每行写明架构、W0、MVP/上线分别需要的证据，后期验证不抵扣前置门槛。

实施阶段将每个需求 ID 对应到实现/配置、用例和结果，覆盖适用的正常、错误、越权和恢复场景。第 7 章的设计、部署、契约、集成、验收和运维交付物分阶段形成；第 8 章的业务、合规、目标环境、量化与供应商决策以相应阶段实证和授权为准。

先固定前三列，独立复审后再填写后三列。架构阶段须有足以判断关键安全、正确性、扩展性与运行可行性的证据。跨阶段项目仅对已经证明的范围判定。W0 按目标宿主验证首条真实受控链路；MVP/上线按真实业务、供方、环境及负载检验。架构裁决通过仅允许把该路线用作 W0 设计依据；正式 W0 实施及 MVP 各有评审与授权。冻结后增加阻断须指出遗漏的原始要求、实质变更或足以推翻先前判断的新证据，只复审受影响部分。

## 验收方法的外部依据及本项目取舍

- NASA《系统工程手册》附录 C、D 要求可核验、可追溯，并在示例矩阵中给每项要求标明来源、编号和验证途径。§2.4 区分了按规格验证与在预期使用环境确认用途。本表给每个编号指派检查、分析、测试或演示；一个分组内逐编号记证据和状态，一个样本通过不能替整行关闭。FR/NFR/TS 是原件的需求或选型约束，AC 是原件建议的验收场景，条件性能力按启用范围验证。[NASA 附录 C](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) · [附录 D](https://www.nasa.gov/reference/appendix-d-requirements-verification-matrix/) · [§2.4 验证与使用确认](https://www.nasa.gov/reference/2-0-fundamentals-of-systems-engineering/)
- ISO/IEC/IEEE 42030:2019 的公开范围强调架构评估服务于特定用途、利益相关方关切和决策；CMU SEI 的 ATAM 用质量属性的取舍识别风险。在此采用“谁在什么环境触发什么动作、期待什么响应、从哪里观察、失败改变哪项决定”。当前用途是为设计 W0 选基线；产品、业务方、身份/运维方分别关切任务正确、授权及可恢复性。每个架构硬门槛单独判定，不用加权平均抵消一次错误放行。[ISO 42030 官方范围](https://www.iso.org/standard/73436.html) · [CMU SEI ATAM](https://www.sei.cmu.edu/library/atam-method-for-architecture-evaluation/)
- NIST AI RMF 的 MEASURE 2.3 将性能/保证方面的测量放在接近部署的条件下。模型协议可达、受控模型作出不同决策、真实业务目标完成三项分别记录。Google SRE 的 SLO 方法从使用者关心的服务行为选指标；需量化但尚无项目依据时登记使用场景、样本、窗口、指标责任人及确定阶段。上线前由相应业务/运行负责人确定目标和允许误差。[NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/) · [Google SRE Workbook](https://sre.google/workbook/implementing-slos/)
- 上述来源用于编写方法。产品义务来自本页指定的 v0.4.1；这里采用其中公开方法，不声称通过 ISO 认证或执行了完整 ATAM。若方法提示了原件未要求的新功能，登记待决，不纳入当前通过门槛。文档、外部案例、代码检查、项目实测各自标明适用范围。缺样本记待验，装置/条件失效记无效，观测违反判据记失败；已验证的子结果、适用条件与剩余动作分别记录。后续才有意义的项目列验证负责人和失败影响。

### 针对智能体任务的验收设置

1. **任务终局与动作过程分别判。** Anthropic 以运行后的环境状态核验结果，OpenAI 建议用轨迹定位工具选择、交接与规则问题。明镜 FR-06、FR-24、FR-35、AC-04、AC-15 据此分别查工具请求/回传、外部业务收据、任务契约和交付。示例：两项必需材料只确认了一项，即使工具全部返回成功，也只能登记已完成一项，正式交付应为零。[Anthropic](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) · [OpenAI](https://developers.openai.com/api/docs/guides/agent-evals)
2. **允许等效路径，严格验证应守的次序。** Google ADK 支持不同轨迹匹配方式，Microsoft Foundry 分开检查工具选择、输入、结果使用和任务完成。明镜 FR-03/04/06/07/14、AC-02/04/06 将确定性依赖、发布授权、查证和交付前校验列为必守顺序；无依赖工具允许换序，输入已足够时允许少调用或不调用。参数不符、用错结果和额外有副作用的调用分别记录。[Google ADK](https://adk.dev/evaluate/criteria/) · [Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/agent-evaluators)
3. **验证可用性和稳定性时使用不同读数。** Anthropic 与 τ-bench 区分多次中至少一次成功和同题重复全部成功；τ-bench 以目标数据库状态查业务效果。FR-28/29/36/39 与 NFR-09 的随机模型回归，在隔离起点上事前固定任务、版本、评判条件及重复次数，记录逐次结果、有效样本分母和装置失败原因；只跑一次就只报告一次。运行时安全硬门槛按每次真实效果逐笔判。重复试次是离线实验，不能驱动真实操作重试。历史实验不追补未测的成功率、可靠性或置信区间。[τ-bench 原论文](https://arxiv.org/abs/2406.12045) · [Anthropic](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
4. **按任务校准评判者与数据集。** OpenAI 建议保留典型、边界和对抗样本，Anthropic 建议可确定的结果用程序验，需判断的量表与人工样本校准。FR-17/24/34/36、AC-07/12/15 的样本应覆盖正例、应澄清或停止、授权拒绝、工具故障及不合格交付。关键效果用业务权威而非模型评分；确有主观质量项时在启用前以标注样本核误判、记录不确定，模型或规则升级在同一固定集复测。保留反例与失败样本，评测轨迹只留获准引用。各团队的默认阈值、产品、付费评判器和特定行业题库均不作明镜依赖。[OpenAI 评测实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices) · [Anthropic](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
