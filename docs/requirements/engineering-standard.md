# 通用工程开发规范与验证体系需求

**需求版本 1.0，2026-11-23。** 依据用户的当前任务与追加验收整理，供独立 reviewer 和原实施者使用。候选方案和进展见[任务记录](../tasks/engineering-standard.md)。

## 目标与授权

建立跨项目可复用、版本化的 Codex 工程规范。明镜是首个真实验证项目，明镜业务、技术栈和部署架构留在项目实例。未来真实项目补充跨项目证据。本轮授权在专用分支实现、验证、独立评审、提交并通过 Draft PR 交付。合并由用户决定。使用已有工具与额度，保持生产、敏感数据和额外费用在任务范围外。

## 完整范围

1. 生命周期、需求澄清和可观察验收，调查实际仓库、现有代码、技术方案、PR、规则和运行入口。
2. 无原设计聊天历史的独立方案可行性评审，保留项目权威事实。记录技术取舍、ADR、任务计划、会话边界与冷恢复。
3. 代码和架构约束、目录与文档治理、可编辑图、质量与多层测试。
4. 独立代码审查及反馈直接回到实施者。保留已验证的提交、PR、CI 和人工合并。R1 用实际任务接续验收。
5. 沙盒、并行环境和恢复、安全权限与供应链、复用 Skills 与脚本、用户及项目的 Codex 设置。
6. 核对 Space 的当前能力和 Git 的权威边界；运行维护与复盘。C01–C09 是基线，追加领域同样跟踪。

核对 OpenAI Harness Engineering、Agents SDK 实际仓库、Google Engineering Practices、GitHub Actions/Rulesets、Fowler CI、C4/ADR/Diátaxis、Peter Steinberger 和 Simon Willison 的一手材料。分别标注上游已用机制、适配新增和本项目实测。Mac M4、Instabox x64、Daytona 按现有能力分工，正式 ARM64 验收以候选的 GitHub 作业为准。

## 方案评审验收

- **真实兼容性。** 核对实际客户端、版本、模型或路由、工具、角色入口及权限。原生子代理须确认收到完整任务、读取岗位指令及指定资料。创建成功、空任务、通用回执或缺材料都不能作通过证据。
- **输入与输出。** 原始需求和候选方案各有确定版本。交接提供基线、输入路径及摘要、实际审查范围和格式。结果区分阻断性问题、必要修正、可选建议和待实测假设，每条有具体证据。原设计者逐项回应，方案或相关证据变化后确认旧评审效力并适用复审。
- **实际执行。** 至少实跑独立评审、意见返回、原设计者修订、独立复审、进入下一实施动作。验证任务未送达、评审失败、结果不完整或阻断未解时不启动实施。上下文与只读边界以运行机制和实测为证。
- **简单优先。** 优先成熟原生机制。实际客户端无法证明能力时可用独立新会话、人工启动或转交意见。保留原有成功路径，停在真实缺口，不将纯行为约定记作自动工具。小型低风险改动沿用精简流程。
