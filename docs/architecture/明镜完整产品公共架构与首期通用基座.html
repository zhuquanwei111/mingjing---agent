业务开发前 · 真实受控宿主

先满足最小真实宿主、获准隔离环境与实施授权，按原契约执行 W0a A1–A8，再执行 W0b B1–B8。通过 W0 后，在同一组宿主、账本、网关、资料与收件端补验公共基座。不得把新增要求写成原 W0 已经覆盖。

在同一版本的核对任务上跑正例与故障变体，保留同一场景和可关联的 Task/Run。正例从受控知识库取有效出处，用业务 API 核事实，按版本交付并再次打开。负例在受限资料撤回或证据错版时，实际发送/正式写/交付受阻；看到同一份资料的缓存和旧链接均已失效。 指定一个失败 Run：先实际检索取得当时有效的来源版本和页段，保持缓存，再撤回该版本并让任务继续。记录使用点拒绝、被拦动作以及对原产物/拒绝证据的受控引用。

业务开发前 · 失败诊断与评测

由未参与该次执行的人只凭 Task 查到失败节点、规则/模型/工具版本、权限决定及业务/收件实况。评测负责人固定同一批样本和预期，实际复跑正确和植错样本，报告须命中已知错误，保留样本分母、失败原因、原始证据及命令。 失败追查与离线报告必须显式引用上述同一个 Task、失败 Run、来源版本及原产物/拒绝证据。离线评测独立对照权威清单判出旧出处已经失效，不抄在线报错。另用同一构建的合格 Run 作阳性对照，报告须判合格；互不关联的任务不能拼证。

真实运行记录包由宿主、数据、业务/收件、观测和评测负责人分别出具。最小包含构建号、任务/运行/操作/交付号映射、脱敏 Trace/审计、资料定位及撤回回读、PG 状态、预算与收端计数、评测报告。任一项只有安装或方案时，整道开发前门槛仍未满足。

首链接入 · MVP 业务验收

开发开始即复用相同入口、目录、网关、资料/知识、任务及预算账、质量门、收件、评测与事件。业务方只补场次采集、证据定位、复盘规则、排班约束和相关适配。

运营在获准真实场次复核事实、出处与建议；排班服务按原号查有效预约，本人收件端查实际内容/时间/对象。主用例、只复盘、缺证、满位待选、抢同档、改期失败保旧、局部取消和退出续办分别核验。业务事实、收件与整句完成分别判定。

试用、上线与条件能力

试用前按真实用户及业务数据敲定质量尺度、产品埋点合规接通及可用容量，演练回退与基本恢复。上线前以目标负载与恢复目标验证服务隔离、备份还原、密钥恢复及按号对账。

长期偏好、第二供方／代理、第三方代码执行器、复杂灰度、额外评测或商业计量平台分别按选型表触发。AC-17 在基础链稳定后、首次未知类型正式接入前完成。受控知识库已由本轮移入开发前刚性门槛。

两条路径的设计走查

以下为可复核的预期读数。开发前要拿到真实运行记录，MVP 则另查授权业务端和收件端。

路径 A ｜ 有权用户查询指定业务对象的当前状态

入口只接受已知对象和动作。E1 读取 C1 的已发布定义，直接路由到普通查询程序。程序用同一能力标识经工具网关向 D3 的对象服务发起只读请求，服务用当前对象权限返回状态、来源与时间。宿主校验响应对象与请求一致、必要字段齐全，向当前主体返回。

核验口径：服务端保留一次真实查询的决定和返回版本，宿主保留受理及必要审计。模型请求、Temporal 工作流启动、正式业务写入和独立收件均为零。若最终返回前撤权则不释放受限内容。查询超时显示暂不可取；客户端重开不制造业务效果。

若直调本身是正式写，仍走 08、10 和 09。受理新写前先持久登记操作；同步响应超时由宿主对账器接管原操作并展示待核。需要跨进程长期等待时才交给 Temporal。

路径 B ｜ 核对一组证据，合格后登记并交付

经鉴别的业务事件或用户发起核对任务。E1 固定目标与必需证据，PG 同事务登记 Run、启动意图与预算。Temporal 只持有引用。装配器分别从业务和已发布资料取证；已经齐全可直接校验，缺项时 Pydantic AI 按当前目录动态选择“列证据”及“核单项”，后续输入使用上次返回的引用。 公共基座准入再沿同一宿主、核对卡与收件端启用知识查找：从获准资料取页段，业务事实仍查对象服务；此扩展单独出证。

工具已经受理但回执丢失：PG 按原操作号和调用 ID 标待核，Temporal 等待，父预算仍预留。可信回执至或只读查到终局后，先校验来源、版本和配对，去重核销，重核权/目标/资料后原会话只续一次。等待期间撤权或取消，即使迟来成功也不派发后继；产品按真实效果单列。 用户取消时向可取消的子任务和收端按原号发取消，保留各自确认。

质量门就业务必需证据产出绑定版本的结论。合格才登记，再以独立交付号送本人，按号查收据。只有质量、业务效果和本任务所要求的收件均可核验才完成；缺证等待。登记已成而明确交付失败显示部分完成；若收件回执未知，显示“登记已成／交付待核”，只查原交付号。可核实实际模型轮次、工具实收、业务有效行、收件行和本人再读。

三项影响后续接入的公共取舍

以下是对既有架构的本轮细化。对业务特有的预约冲突、改期资格和同一主播能否并占多档，公共层只接收业务权威给出的结论。

取舍实现责任选择理由与失效边界决定是否可复用的验证
D1 · 目标修订与跨业务依赖业务定义维护者声明哪些分项必需、依赖何种事实、条件为真/假/未知怎么办、允许哪些部分交付。宿主协调器验证依赖无环，将子目标及变更版本固定在产品账。同步代码或 Temporal 负责执行就绪项。 旧回执不能直接完成新版。重用需逐项核对象、来源版本、规则、依赖、用途并记录新判定。对比把每种业务的条件写进公共调度器。采用业务声明＋宿主校验，业务规则与 Oracle 由业务方提供。用户删去后继分项时，已发生的操作保留；未交接的新动作按当前修订拦截。跨权威无法序列化关键交接则关闭该受限路径。用两种依赖组合：条件未知→补证，以及并行分项有一项失败时允许部分交付。并发改意图、重复回调和迟到回执，核实际新增写入/交付数。若须加业务分支到公共核心，重审任务契约。 用户删一支、保留一支时，保留分项继续。
D2 · 异构写入、查单与取消执行方声明幂等范围、查单/取消能力、明确未受理的证明及原始状态映射。区分受理/在途、已生效、明确未生效、结果未知。取消请求及是否可撤销另记。宿主记录统一事实状态和适配器版本，保留原始状态引用。对比由宿主推测外部结果。采用执行方证明＋宿主核销。网关超时不推断失败；查询无结果只有在来源明确保证已过一致性窗口、且证明原请求不再到达时才算未受理。同号同载荷、可安全去重且重核获准才准重发。首次派发前不具备操作绑定、去重和可查事实的出口关闭正式写或只留草稿。满足准入后发生丢回执则保留待核。冻结公共核心，由独立接入者接第二个有副作用的异步能力。故意丢回执、重复通知、撤权和取消，分别核发送、有效效果、计费和下游收件。缺证明先换适配器或关闭该出口，普遍不适配才重审契约。 对可取消的父子/外部任务还须观察实际收端收到的取消与确认，迟到后新增模型、子任务和交付均为零。
D3 · 多来源撤回与派生物发布者负责来源版本及其适用范围；资料模块登记消费者、版本依赖、派生物与进度。更正为新版本，明确旧版是否仍允许用于历史查询。受影响的派生在重新验证前限制正式使用。使用点优先从权威目录取得当前判定。对比仅等缓存过期或只发一次通知。采用使用点拒绝＋可重放的变更通知/确认。发布者失联、依赖不全或无法建立撤回和交接先后时停止受限使用；保留既往合法交付和审计原件的访问限制。两来源合成一产物，撤回其一，令索引离线、缓存命中且通知重复/乱序。核模型新收、旧链接、正式交付均无失权内容，消费者恢复补扫。若检索引擎难以拦截，只重选索引/出口或关闭检索。 另测漏通知和发布/撤回并发，补扫前拒用受影响版本；不依赖该源的产物仍可正常使用。
