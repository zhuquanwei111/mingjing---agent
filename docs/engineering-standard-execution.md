# 工程体系可执行性审查

范围沿用 C01–C09，另核对设计关卡、ADR 与 Space、供应链、维护与版本。人工决定、Agent 发起的流程和命令强制的检查分别记录。项目本轮实测结果集中在[任务记录](tasks/engineering-standard.md)，运行候选以对应 PR 及 GitHub 日志为准。通用规范和适配的一手依据见[来源和证据范围](../engineering-standard/sources.md)。

| 项目 | 机制及一手依据 | 实际触发方式 | 失败处理与可复验方法 |
| --- | --- | --- | --- |
| C01 需求、兼容与验收 | [任务模板](../engineering-standard/templates/task.md)与四项实施边界。采用 Agents SDK 的 implementation-strategy 经验 | Agent 识别有影响的变更，在计划记录需求、兼容、范围外及现有路径 | 缺关键取舍交给用户判断。用本任务和其独立方案评审核对每条验收、权限和对应输出 |
| C02 调查与权威入口 | 根入口、Git 代码、测试及历史记录。采用 Harness Engineering 的导航思路 | 开始任务时核对 Git 与相关入口，`make check` 自动检查导航 | 失效或越界链接返回非零，恢复前纠正入口。核对 C4 视图、当前 P2 路径、历史报告和 PR 实际 head |
| C03 计划、边界和冷恢复（R1） | 单一任务记录、只读状态脚本、仓库接续技能。采用 ExecPlans、Agents SDK 与 Codex 的仓库发现机制 | 新会话按任务位置或技能调用，从仓库读取当前状态 | 对齐旧计划与真实工作区。Mac 新会话实际执行记录内命令并结束只读恢复；复验以命令、SHA 和下一步为准 |
| C04 代码与架构 | Python 静态导入检查、行为测试、编辑式架构图。采用 Harness Engineering、C4、Google 审查维度和 Willison 反例方法 | `make check` 与影响范围测试，Agent 更新架构或接口 | 静态边界损坏作业失败。已有架构反例覆盖传递导入，P2 行为仍由实际入口验证。通用 lint、类型、动态导入和生产安全各需对应证据 |

| C06 独立代码审查与 Git 交付（R2–R4） | 实施者发起独立评审、直接读反馈，独立分支提交、Draft PR。采用 Agents SDK、Google、Peter 公开实践及 GitHub PR | 实施候选完成聚焦检查后发起 reviewer；获授权后实施者提交和更新同一 PR | 缺结果、确认问题或候选变更时处置和复审。核对应审差异、直接反馈、实际提交、Draft 状态和 CI。`#2` 的已验证人工合并保留，当前合并决定归用户 |

| C11 目录、ADR、图和 Space | [ADR 0001](adr/0001-versioned-engineering-standard.md)、C4/Diátaxis、Git 原文和 Space 引用。采用方法作者及 Space 官方文档 | 决策变更与实现同 PR；需要协作时人工指定 Space 页和 Git 来源 | 拒绝失效及越界本地链接，纠正不同版本的引用。复验两幅 Mermaid、ADR 和真实页面检索；协作写入保留为按需动作 |

## 新原生子代理路径的最小验收（待真实执行）

1. 在 Codex 的新主会话中核对项目级 `.codex/agents/solution-reviewer.toml` 是否被发现；输入一份可读取、固定版本的需求与候选方案。
2. 让主 Agent 创建 `solution_reviewer` 子代理（可用时显式采用 `fork_turns: "none"`），要求回执任务编号、方案版本和来自实际材料的证据，不提供原设计聊天历史。
3. 主 Agent 直接收到具体问题，原设计者逐项回应并修订；对一个缺资料或有阻断问题的负例不得记为通过。记录实际调用、回执、发现、版本和回流结果。
4. 如果当前客户端不支持角色选择、上下文隔离或消息回流，按文档使用 CLI 备用或人工全新会话，并如实标注。**本次 PR 的 CI 只验证配置、测试和项目回归，不能代替这项实时运行验收。**

## 关键关卡可复验脚本

```sh
python3 engineering-standard/adapters/codex-cli/start_implementation.py \
  docs/requirements/engineering-standard.md docs/tasks/engineering-standard.md -- make check
```

示例复用本项目已有需求和任务；实际使用时指定本次获准的首个动作。调用时自动开始评审，CLI 退出与结构化结论独立核验。失败后由原设计 Agent 读取具体意见，写回任务和计划，再用相同入口触发新 reviewer。明确通过后才检查候选是否变化并启动命令。验收记录包含冻结需求、两个计划版本和相同动作的摘要、Git 基线、两轮独立回执、逐项处置和后续动作结果。日常按项目指定入口使用。直接执行命令或未经此入口的编辑由既有项目流程处置；本入口权限与 CI、发布、人工验收分别生效。

原生子代理成功创建后，仍要求实际收到任务短标识、角色、两份资料及具体证据。开源仓库记录了空任务、仅收到消息外壳和假完成等问题。将通用回执、空报告、输入不匹配、超时、异常事件或未解决的问题作为阻断。原生首次及后续投递在本机实跑。空请求实际创建子代理后只收到无任务回执，流程未放行。另用形状相同的合成报告验证检查器拒绝；当前客户端未复现有内容的请求被平台丢失。[投递报告 #25458](https://github.com/openai/codex/issues/25458) · [空消息报告 #36321](https://github.com/openai/codex/issues/36321)

## 首轮复盘

- 恢复一次，Mac 新会话正确找到任务、当前候选和下一项，实际只读命令退出 0。后续真实任务继续记录恢复是否需要用户补背景。
- 反例优先验证容易误报成功的节点，包括包导航失效、技能错配、评审没有结论而后续命令仍获执行。命令的退出码、文件变化和 GitHub 作业结果作为核对依据。
- 首次反馈耗时以对应 PR 的 CI 时间为准。使用现有订阅和标准 GitHub runner。尚无跨项目效率数据或生产验证。
- 用户审核、后续目标分支变化、合并后验证以及未来真实项目采用，是接着积累证据的节点。发现问题时由该领域维护者决定更新通用规范、技术适配或项目规则，并在下一真实任务复验。
