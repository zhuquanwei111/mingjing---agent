# Codex 设置与环境分工

本页说明明镜如何适配个人设置、项目配置和已有运行环境。配置目标是让 Agent 在已授权范围内完成开发、验证、独立审查和 PR 交付，由用户决定合并。图形界面是日常任务入口，文中的命令由 Agent 执行；用户可以自愿复核，不承担搬运日志或审查意见的工作。

## 三层设置分别核对

| 层次 | 本项目的选择 | 如何判断实际生效 |
| --- | --- | --- |
| 个人默认 | 保留用户选择的模型、推理力度、认证和已有工具。根据实际任务需要调整，不照抄他人旧模型参数 | 以用户当前客户端显示和当前会话提供的能力为准；不把云端代理的配置当成 Mac 的配置 |
| 项目默认 | [`.codex/config.toml`](../.codex/config.toml) 设置 `approval_policy = "on-request"` 与 `sandbox_mode = "workspace-write"` | 项目必须受信任才会载入项目配置；文件通过 TOML 解析只证明配置文件有效 |
| 会话与管理策略 | 当前会话的启动设置、适用管理策略和实际可用工具共同决定能力 | 核对当前项目根目录、可用读写和执行工具、审批限制及所需连接；不能由仓库文件推断这些权限都已获得 |

这些项目值仍是 OpenAI 文档支持的配置。`on-request` 允许必要时请求审批，不表示每个普通动作都要再次确认；`workspace-write` 也不等于自动获得网络、GitHub 或沙盒供应商的访问权。项目默认不能覆盖更高优先级的强制限制。

在 Mac 的项目会话中，Agent 首次执行任务时应确认当前 Git 根目录是用户打开的 `mj-agent` 仓库，读取根规则并报告当前分支。若客户端没有加载项目设置或某项工具受限，记录实际状态和具体影响，再按客户端当前入口处理；不得用放开全部权限、改认证或新增供应商密钥作为默认修复。

本轮只核对了仓库配置文件和当前云端工作区。未连接用户的 Mac 会话，因此个人设置、项目受信任状态及该会话的实际权限仍是外部待核实项。核实时只需要设置名称、非敏感值和实际能力结果；不读取、保存或要求用户粘贴认证文件、环境变量全集、令牌或完整个人配置。

## 环境使用与资源归属

| 环境 | 用途 | 本轮可作出的结论 |
| --- | --- | --- |
| Mac mini M4 | 用户的图形界面主会话、代码检查及需要时的本地冒烟 | 原生 ARM64；本轮没有在该机器运行新候选，不能将 Linux CI 称为 macOS 运行验证 |
| Instabox | Linux amd64 联调、复现和辅助回归 | 既有 P1/P2 记录可以说明此前运行情况；新候选仍须有本次结果，不替代 ARM64 正式验收 |
| Daytona | 有实际需求时使用的隔离试验环境 | 本轮未连接实例；架构、Docker daemon、Compose、网络、权限和生命周期须在使用前核对，不把“用户拥有沙盒”等同于“已准备好” |
| GitHub Actions | 干净、可追溯的正式 ARM64 检查及独立 amd64 辅助检查 | 以 PR 当前 head 对应的完整 job 日志为准，具体入口见[开发流程](development.md) |

任务隔离使用 Git 任务分支和必要时的独立 worktree/checkout；每个运行目录只归属一个正在执行的任务。P1 和 P2 各自使用专属 Compose project 与生成凭据，清理只能作用于本次资源。不要对别人已在使用的目录启动第二次验收，不运行全局 Docker prune。对资源归属的核对不要求为展示并发而额外启动服务。

Daytona 是可选执行路径，本任务不为使用它而购买或新增服务。缺少当前实例连接不妨碍使用已经可用的 GitHub ARM64 路径；是否采用 Daytona、实际验证了什么，继续写入[配置总账](tasks/codex-development-configuration.md)。

## 重复流程用什么承载

| 工作 | 当前承载方式 | 保留或调整的理由 |
| --- | --- | --- |
| 语法、文档入口、代码边界与验收 | 根 Makefile 与仓库脚本，CI 调用相同入口 | 确定性工作交给命令，失败以退出码呈现，避免依赖每次重新描述步骤 |
| 复杂任务的完成条件、决定和接续 | [任务计划约定](PLANS.md)及该任务已有记录 | 状态随代码版本保存；轻微改动不强制创建计划，接续时核实真实 Git 状态 |
| 独立审查和反馈处理 | [现有开发流程](development.md)中的独立 reviewer；原 Agent 修复、复验 | R2–R4 已在 P2 开发中实际奏效，无需为形式引入新 review-loop 或强制安装 helper |
| 可重复且现有入口不足的专门工作 | 发现真实重复负担后再封装小技能 | 定义触发、输入、产出和失败状态，并验证一次代表性任务；没有项目技能目录本身不是缺陷 |

这里采用的是 OpenAI Agents SDK 团队的“可发现的短规则、明确触发、脚本验证”和 Peter Steinberger 的“任务相关文档、精确提交验证、明确交接”机制。上游团队采用过这些机制，不等于本项目的每一条改动都已被上游团队验证。本项目的实施和运行证据分别记录在[配置总账](tasks/codex-development-configuration.md)与 PR。
