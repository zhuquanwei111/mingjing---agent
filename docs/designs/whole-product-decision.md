# 明镜智能体 · 完整产品工程验证与技术选型

## 设计者建议

首选**经调整的路线 B**。把 Python 应用嵌入明镜的任务体系，PostgreSQL 保存产品任务、操作、共享预算和交付事实；普通程序可在业务端直接完成。需要跨进程、跨时间恢复的任务由 Temporal 调度，需要动态工具决策的环节才使用 Pydantic AI。对所有副作用增加可恢复的产品操作记录，对需要续接的 Agent 工具按原调用保存受控检查点，外发经可治理的实际出口处理。上述调整改变了原先把整段 Agent Loop 交给一个重试 Activity 的做法。

业务写入的事实权威归业务方，交付由接收方确认，质量判定归相应业务验证器。明镜维护宿主身份与动作映射、启动意图、工具/模型派发、未知费用保留、查询核销和质量后交付。这些职责可以作为后续各能力的公共设计依据。宿主可按明确替换条件换成成熟应用，Agent 与调度可各自替换。当前候选中，B 提供同一套固定栈内的持久调度、受控引擎载荷、原生延迟工具和对账样本；适合明镜自有身份、业务服务和 App 交付的设计。代价是维护轮次检查点以及一个独立调度服务。没有总成本或吞吐量的实测排名。

**最接近的替代是 Agno AgentOS。** 若 App 需要直接复用一套 Agent API、会话、队列和运行（包括中断后按原 requirement 续接），它能减掉一部分 Python 宿主。真实用户、业务端 ACL 与交付依旧要整合，且受控参数转换、账本、撤权和模型出口仍由明镜承担。Windmill 在直接复用脚本、工作流和管理界面时更有价值；DBOS 在可接受稳定执行器或具备失联判定时可替换 Temporal；Mastra 是已有 TypeScript 后端时可以直接比较的 Agent/工作流一体路径。各路线均允许同样的受控引用、幂等账和网关改造。业务后端技术栈、实际需要的管理界面及目标运行资源尚无足够输入，首选的理由不包含臆测的人天或对旧开发的偏好。

## 哪些结果会改变选择

先列可能改变核心的四件事。第一项异步样本以及进程失效、受控引用等可隔离的部分已在本轮实测；涉及实际身份方、业务端提交和目标部署的结论分别归到下列明确阶段。需求全表逐组列有局部影响和最迟时点。[23 组 / 76 个原编号的逐组复审](whole-product-review.md) · [其他成熟方案、原始来源及入围标准](whole-product-alternatives.md)

1. **能力能否独立接入。** 同步型由 #5 验证三入口；可延迟、能产生副作用的外部工具由 #12 验一入口、#17 验三入口。两者都显示需要明确操作标识、权限、预算、是否可核查、版本及结果。W0 首次将目标宿主三个入口接入同一异步能力。基础链路稳定后冻结公共代码，再登记真正事先未知的实现，依 AC-17 复核。若特定实现需改数据转换，归能力适配；如果每种实现必须改公共派发或循环，调整能力契约，优先比较 AgentOS 原生 external execution。未来新增业务类型继续采用同一判据。
2. **动态回合、模型重试和升级。** 五条路线各有独立重启、配对、收据、计费证据；完整状态迁移、模型费用不确定时的安全后续和下一次正式交付中断，均不能从这一个故障窗口外推。在 W0b 由目标 Agent 宿主验证申请、挂起、继续、取消与版本排空。在途结果变可查后如何继续决定轮次适配的保留；若受治理适配仍不安全，换 Agent/网关，调度器按自身证据单独判断。
3. **真实身份、受理与正式出口。** 已实测单一授权域发送的先后、业务服务同库终核及模拟对账。实际 App 身份源、真实业务 ACL 和可观察的交付端尚缺首条贯通。W0a 测动作发生前一刻的授权和操作号；只有产品状态而没有收端事实的条件不得关闭。不同业务是否能提供独立查询/去重决定各自可启用的操作。
4. **常驻服务与成熟应用替代。** 嵌入式调度可少一项服务，完整应用可少开发运行 API、控制台或暂停队列，同时改变数据可见域和运维责任。若宿主只允许 PG 且有可靠接管，按 #15 同题选择 DBOS；若已有 AgentOS/TypeScript/Windmill 宿主或目标部署要求复用其能力，拿目标宿主在相同端点重验上表，并确认授权、发行许可及在途迁移。无此条件时不同时引入多个引擎。

现有 P2 可独立保留经过验证的数据契约、权限/幂等回归、实际收端样本及兼容时的质量规则（#6）。旧执行核心没有整体继承的依据，正式迁移包、生产账号及已有业务数据均不在本轮范围。PR #7 的 R4 仍给出历史 W0 设计结论；下文记录独立总评及设计者处置。本轮仅处理完整产品设计。

## 首轮独立总裁决与设计者处置

全新上下文的独立总评审者对固定提案 [5a3c2c5](https://github.com/zhuquanwei111/mingjing---agent/commit/5a3c2c5cf2c00509e503fc4b44280390b0409bf5) 裁决为**关键证据不足，暂缓采纳路线 B 为完整产品开发基线**。评审者对照需求原件和原验收主表，23 组中每组的编号逐个对应，共 76 个。另读取五条路线的固定代码、收端原始事件、引擎记录及归档，独立重算关键计数。五条有权样本同为 1/1/1/2/1 的结论成立。#7 的 W0 设计基线有效。

设计者接受这一意见。工具生效后换进程续一次，不能推导模型收单后重复收费或未知转已知也得到控制。原 #12 的 `charge_model_slot` 只限制任务内总次数，首轮 `agent.run` 返回后才持久化操作号和调用；`Round.run` 遇未知后结束，`Notice` 面对活跃且已知的回执明确报错。这两个窗口直接涉及 FR-06/09/28/29/30/37、NFR-01/03/10、AC-08/14/16，且两者均可现在隔离关闭。所需条件已在得知新结果前锁定：

| --- | --- | --- |
| 模型首轮已到达并模拟收费，回执未被产品记录时强杀或断响应 | 同一持久轮次，恢复与重复触发后实际模型收到 1 次、模拟费 1 笔；未知保留预留，无工具、无交付；原接法及新接法分别记录。 | 按轮次唯一认领的模型出口和对账；总次数限制不能替代。 |
