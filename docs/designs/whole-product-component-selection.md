# 完整产品通用能力与组件选型表

**设计结论。** 采用 #14 裁决的 Python 宿主、PostgreSQL 产品账、Temporal 持久调度、Pydantic AI 动态决策。保留逐操作/逐轮唯一模型派发资格，以及工具状态未知时持久等待、查清后回到原调用一次的两项调整。新增产品能力先落实到这些边界及现有业务接口。首期选择是拟实施的职责分工；只有表内标明的实验范围已有运行证据。

依据为 v0.4.1 原件（SHA-256 `75ac634a98393b5f99fb28901a6a91bc7431290143b6458bbf1f9a2af5f23062`）。图 1 的控制、执行、数据与能力、治理与观测是四个逻辑视角。图 4 区分业务事实、批准资料、会话、检查点和可选记忆。图 7 用运行标识关联轨迹、评测、用量和审计。沿用[76 项逐项验收](../requirements/whole-product-acceptance-results.md)与[技术裁决](whole-product-decision.md)。10 项机制实测、45 项局部实测、13 项指定场景未测、7 项文档核实、1 项按启用条件验证。下表补选型与责任，各项原判和分阶段证据要求继续有效。

**时间与证据。** “方案复审前”指 W0 真实宿主结果回填后、首期 MVP 实施方案送审前；届时需有接口所有者、可取得的数据、选定方案或阻断决定。业务通过须在随后获准的试用中取得。无宿主期间 W0 实测为 0/16。E5 指 A/B 三入口、Agent、预算及质量样本；E6 指候选独立质量函数及 15 项测试；E10/11 指回执丢失和单授权域首次交接；E12 指真实工作进程中断、原调用恢复和模型派发修订；P1 指旧 AT11。它们均不证明明镜 App、真实排班或收件已联通。[原实验汇总与固定提交](whole-product-decision.md) · [E6 代码](https://github.com/zhuquanwei111/mingjing---agent/blob/c22aff11d48bd6bc0accf245e799e889e7c8f4a1/app/src/mingjing_agent/quality.py) · [P1 原始记录](../../p1-walking-skeleton/evidence/lima/AT11.json)

## 知识库的取舍办法

在同一隔离资料集分别给两个租户导入相似材料；发布 v1、纠正为 v2、随后撤回，另加未发布和过期对照。固定解析/嵌入版本、维度、切分策略、查询集及人工参考出处。比较从摄入、解析、索引、授权召回、原文页/段/时间码、上下文、模型输出到最终交付与旧链接兑换的全过程。覆盖缓存命中、在途撤回、索引未清理窗口、换嵌入版本与维度后重建/切换/回退。撤回应先使访问失效，再清理物理副本并留处理记录；未满足最小出处时返回缺证。

RAGFlow 可直接复用材料管理、解析与检索界面/API；核版本、许可、所需引擎、运维和明镜对象级权限适配。组合方案复用 Docling 解析与 pgvector 查询，由数据团队负责 ACL 前置过滤、严格复核、索引生命周期、引用和谱系。两者同测零越权/撤回残留、正确版本与出处、相同样本下的检索质量、维护步骤和必需服务。安全硬项全过后，优先选能直接复用更多且实际维护步骤较少的一条；仅一条过硬项则选该条；两条都失败则停用检索并重选受影响的资料边界。只按指定报告 ID 找上次改进项可先完成首期场景。[RAGFlow 文件管理](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/files_dataset_document_management.md) · [Docling](https://github.com/docling-project/docling) · [pgvector](https://github.com/pgvector/pgvector)

**上游接口与引入成本。** Pydantic AI 的历史消息接口可用于组装输入；SDK 版本与实验锚点须逐项对齐，消息修复不能作为业务回执。LiteLLM 的自动重试/降级增加一次调度与出口，只有能关闭冲突策略并通过丢回执同测才启用。Promptfoo 可调用 Python 断言，新增回归 CLI；Langfuse 有提示词版本管理，需额外服务或批准的数据出口。OTel 传输与 PostHog 产品事件各自可失败。均未在本轮安装、接通或测得总成本。候选进入实测时记录选定发行版、许可/商业功能边界、必要进程、锁文件、源端和收端、实际维护操作；有版本兼容或授权疑点时留在候选栏。[旧包引入条件](../../mingjing-codex-engineering-v1/03_TECH_STACK.md) · [Pydantic AI](https://pydantic.dev/docs/ai/core-concepts/message-history/) · [LiteLLM](https://docs.litellm.ai/docs/proxy/reliability) · [Promptfoo](https://www.promptfoo.dev/docs/configuration/expected-outputs/python/) · [Langfuse](https://langfuse.com/docs/prompt-management/features/prompt-version-control) · [OTel](https://opentelemetry.io/docs/concepts/signals/) · [PostHog](https://posthog.com/docs/product-analytics/capture-events)

**验收方法依据。** 对可写工具，分开记录调用轨迹和目标系统最终状态；对复盘建议，以版本化样本、业务专家判据和可重查出处校准主观评价。这样能识别“工具说预约成功但排班无有效单”和“引文存在但不足以证明开场动作”两类失败。此做法参考 Anthropic 的 Agent 评测方法与 OpenAI 的业务评测建议，项目门槛按原需求与用户业务规则冻结。[Anthropic · Agent 评测](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) · [OpenAI · 评测实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
