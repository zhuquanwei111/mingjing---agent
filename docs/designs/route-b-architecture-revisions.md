## RB-01　准入和修订后的实施顺序

先复审 RB-02 至 RB-07 的协议与实验证据，确认高影响缺口可否在仅用合成数据的限界内继续。原设计者提交材料，独立评审者作出通过、修订或阻断的判断。用户决定实际业务语义、可接受限制和候选取舍。需要先验证才能判断可行性的项目可作为独立、可丢弃、另行批准的技术实验；不能用计划替代实测来关闭阻断。

| 顺序 | 范围及通过证据 |
| --- | --- |
| 1．W0a（获准后） | 一个有权主体经真实 API 提交中立“核对清单”任务，PostgreSQL 写入并读回，Temporal Server/Worker 调度一项受控程序。工具结果经可信验证后，先提交、再交付。用独立接收端分别计数，并在新进程按 Task/Run 读回结果。无权、跨租户、缺项、撤权、启动中断、回执未知各有负例。 |
| 2．紧接 W0b | 原封复用 W0a 的身份、操作与交付出口。接入 Pydantic AI，按构造的不同任务动态调用至少两种工具，回传配对结果，测中断与终止。协议夹具可走正常 SDK，兼容检查使用获准的本地真实模型、合成数据，留存实际请求数、调用数及业务得分。运行完两段才能判定 Agent 集成。 |
| 3．正式 MVP | 产品负责人另定哪类明镜用户能完成哪一项真实任务、权威数据、可执行动作、交付对象和可测价值。用批准的真实身份、环境、预算和负载验收后才讨论真实流量。知识、评测、父子预算等仍在全量需求内。 |

继续条件是按同一提交从 API、产品库、引擎历史、工具、质量记录到接收端逐笔对上。强制出口有旁路、恢复改变业务事实、无法约束敏感历史、未知操作可能重发时，暂停该路径，修订或重选。旧 P1/P2 及 #6 的工作区、凭据、在途运行不迁入 W0。回滚先停止新受理，排空或登记在途动作，保留接收端和原账本可核对。

## RB-02　产品状态、启动与业务效果

| 标识 | 权威和约束 |
| --- | --- |
| Task / Run | 产品库保存任务以及每次显式运行。唯一 `(tenant, client_request_key)` 对应规范化输入指纹，重复同输入返回既有任务，不同输入返回冲突。一次产品 Run 对应唯一启动意图；用户要求重新执行须新 Run，并重新判断是否允许产生新业务效果。 |
| Workflow ID / Temporal Run ID | namespace 与不含业务内容的稳定 Workflow ID 唯一绑定产品 Run。引擎 Run ID 保存为链，记录首次、后继及原因，包括 Continue-As-New。引擎历史只证明调度进度。查到同 ID 需核对绑定，运行中冲突和已关闭 ID 重用均不得创建第二次执行。 |
| Operation / Attempt | 业务幂等域按租户、能力、业务操作号唯一，存动作版本、目标与输入指纹，跨 Activity 重试、Worker 切换和重复回调保持不变。每次尝试单独编号；数据库约束拒绝同键异参。同一业务效果跨产品 Run 仍用原键，除非明确获准创建另一效果。 |

宿主在**一个数据库事务**内提交 Task、Run 和待启动意图。派发器短事务领取带到期时间的意图，再用固定 Workflow ID 启动。启动超时或进程退出，扫描器按同 ID 查引擎并比对首次 Run/绑定；已启动则补记，明确未启动且仍在安全窗口才重试。已取消或失权先封住新派发；若引擎已启动，记录事实并请求停止。历史已过保留期、查到不同绑定、库与引擎版本冲突或外部回执不明时停在待核，禁止猜测重启。引擎完成而业务未确认时，产品状态保持待核或部分完成。

在调用有副作用的服务前落 Operation 意图和预算，外部请求后归档可信回执。可信供应商查询或收端账本证明业务效果。恢复必须交叉核对产品库、引擎历史和独立接收端。备份分别记录产品库恢复点、引擎快照/历史水位、回执和规则版本；从备份恢复先关闭派发，重建关联，再按外部记录补账。迁移采用可回读的增量模式，先验证旧 Worker 能读取旧数据。回滚切换新任务的版本，保留已生效操作及新字段，禁止用回滚快照抹除外部效果。

**指定故障验收**：在库提交前、库提交后引擎调用前、引擎成功回执回写前、业务写入成功应答丢失后分别杀进程，另测两个派发器竞争、重用已结束 ID、保留期外和同键异参。每次对齐 Task/Run/Operation/Attempt、引擎链和接收数，预期分别是无已受理任务、仅一次启动、补记同一启动、仅一次效果或待核；冲突不产生新发送。现有 P2 提供固定 ID、拒绝重用、按既有绑定 describe 的可借鉴代码；新组合的提交窗口仍待验证。 [P2 启动适配](https://github.com/zhuquanwei111/mingjing---agent/blob/fdf04240eba747a9a681a1dad627da22d4b89cdd/core/src/mingjing/temporal_adapter.py#L120-L155) · [Temporal 标识语义](https://docs.temporal.io/workflow-execution/workflowid-runid)

## RB-03　撤权与并发中的真实发送

宿主从经验证的登录身份及组织关系创建任务，绑定租户、主体、资源版本、使用目的、动作及允许接收方。请求体的 tenant、模型挑选的工具、任务创建时的权限和缓存都不能授予新权限。五个最终核权点分别在受限数据读取服务、模型网关写出请求前、工具网关写出参数前、业务方正式提交前、交付端发布或读取结果前。恢复时只保存受控引用，重新取资源及授权；重连、流式后续块、分页和下载均按适用动作重新授权。权限未知、身份源不可达、版本失效或出口无法控制时，停止该动作。

建议把撤权与最后的发送许可按同一主体/资源权限域排序。出口持有唯一发送权并校验当前授权代次；撤权先阻断新许可，作废未发送许可。队列记录及已领取许可本身不赋予发送权。对本方能控制的接收方，用同一顺序在接收/提交处再校验代次。对外部模型或供方，明确记录三个时刻：撤权的权威提交、不可撤回的请求交接、接收方确认。先撤权则后续交接必须是零；先交接则保留发送事实及在途状态，能够取消的尝试取消，返回结果再次核权。请求一旦发出无法保证对方在撤权时刻停止处理。若身份源和出口无法提供可验证的共同顺序，或业务要求收方在撤权后一律不得接收且无接收侧控制，该类受限资料禁止进入此出口。短 TTL 不能解决这段竞态。

操作意图短事务落库，数据库事务不跨模型响应或外部 HTTP 往返。出口只串行化最后一次核权与请求交接，不持闩等待完整响应；出口崩溃先核对在途发送再放行。对持续执行和暂停恢复各注入五处撤权，另交错“权限读取后、真正交接前”和“已交接、未回执”；记录权威提交、出口判定、接收端时间及序号、锁/队列等待和撤权生效的 p50/p95/p99、最大值与样本量。试验已覆盖指定屏障，尚无目标身份源的竞态上界，不声明延迟达标。 [实验模型请求仍持共享锁](https://github.com/zhuquanwei111/mingjing---agent/blob/553114d2114cc77081c415ad1697e74be282c9a8/lab/architecture/b/runtime.py#L83-L90)

## RB-04　适配器能力、取消和共享费用

| 已核实的供应商能力 | 允许的恢复动作 |
| --- | --- |
| 幂等键、同键同参约束和可信查单 | 重用稳定键并先查单，确认未受理且仍有授权、额度时才重发。查单暂时未找到须区分最终一致窗口和终局未受理。 |
| 只有查单或终局回执 | 用业务关联号查单或验回执。存在并发受理或结果不明时维持未知；只有合同能证明前次绝不会生效才可再派发。 |
| 只有幂等键 | 仅在供方保证的幂等保留期、作用域和参数绑定内按原键恢复。有冲突、期限不明或过期则待核。 |
| 两者均无，或无法约束收费上限 | 一个已发送的有副作用请求不自动重试。登记待核、所需凭据和责任人；无可执行费用上界时禁止进入硬共享预算自动路径。模型重采样也可能再次收费。 |

取消是产品侧禁止新派发的事务状态，向运行中的子任务和可取消的外部请求传播，保留已发送、已生效和未知三类事实。回调需验证来源、租户、业务键和指纹，使用唯一事件/收据号去重。迟到成功只补事实和结算；下游入队与实际发送均复核父任务状态。无法查单的人工核查记录依据、操作者和结论，不能以撤销请求成功冒充撤销效果成功。

每次派发前在同一父预算账本原子预留上界，唯一键含父预算和操作号。可分次计量，按唯一计费事件幂等核销；剩额为上限减已结算及未结预留。在途未知保留额度，只用可信终局事实释放。供方实际超出保留时按实记账、标异常、冻结新派发并对账；不能丢掉实际费用以保持漂亮的上限。子任务汇总返回已完成、取消、未知原因及实耗/预留。新增产品验收覆盖上述四种适配器、重复/乱序回调、取消与发送竞争、预留崩溃、父预算竞争。 [独立收端与最终原始日志](route-b-review-evidence.md)

## RB-05　可信质量记录与交付

沿用 #6 的纯判定库，可信调用者限定为宿主侧验证服务。验证服务通过任务、租户及能力版本读回业务收据或受控证据库，核实来源身份、输入/输出版本、必需条目、内容摘要与可用性，再构造库的输入。正式提交端只接收受控记录 ID。模型文本、工具的 success 字段或客户端自报的 ready 均不能充当凭据。保存判定时绑定授权域、任务、规则版本、证据版本集合、输出摘要及判定时刻；到期、撤回、内容变更或验证服务不可用则重验。提交与交付各自最终核权、核对同一质量快照，使用幂等键和真正的接收回执。已发生的外部动作可为 confirmed，同时整项任务仍为不可交付。

目标链路采用正例提交一次、交付一次，重复读取或重试不增加业务交付；缺项、错误来源/版本和验证不可用逐一测，提交、交付接收数均为零。另测质量通过后撤权、证据换版，以及提交已生效但交付前撤权。最后一例预期提交一次、交付零次。已有 15 项测试和 A/B 夹具分别证明局部行为，尚缺同一新宿主的提交与交付收端证据。 [固定库与复跑方法](route-b-review-evidence.md)

## RB-06　按同一硬门槛择优

推荐 B 首先进入 W0 可行性评审。可复查的优势是同一 Temporal 上直接使用原生动态循环，新增符合既有契约的能力可以注册接入。A 的目录、发布和回执则有直接复用证据；应逐项保留负例、契约和可独立适配的机制。Windmill 是最值得挑战 B 的完整应用，Dify 是具有界面和知识复用价值的另一候选。若完整应用通过同一硬门槛且可减少明镜必须承担的通用代码或服务，重新排序。实验行数、三份研究的票数和初期用户数均不构成长期成本测量。技术、发行、许可、迁移及比较试验见[候选与证据台账](route-b-review-evidence.md)。

## RB-07　恢复、升级与运行验收

旧实验中整个 Agent 循环是一项 Activity。W0b 先固定重试边界，保存受控的轮次标识、模型/工具请求 ID、结果配对、模型/规则/工具版本、操作键及预算状态。敏感消息存于受控存储，Temporal 历史、搜索属性、错误与日志仅留不含正文的引用；恢复需重核访问权。若整轮重跑可能重复收费或发送，禁止盲目重新生成；先查可核实结果，无法核实转待核。比较整段 Activity 和按模型/工具步骤持久化两个候选；原生插件只计作可验证的实现选择。细粒度恢复若把敏感正文写入引擎历史，须改为引用、验证编解码与密钥策略，或停用该方式。

固定旧/新 Worker 和依赖后在四处终止进程：模型请求交接后答复持久化前、工具请求生成后执行前、工具效果产生后结果回填前、结果回填后下一轮前。保存真实历史样本，核对消息配对、接收计数、收费与授权，再做匹配/交叉版本离线回放、新任务切换、旧任务排空、回滚。交叉回放有非确定性时保持原版本处理在途任务，切换新任务路由；旧 Worker 只在无在途运行和历史回放策略满足后退出。 [P1 原版升级记录](https://github.com/zhuquanwei111/mingjing---agent/blob/fdf04240eba747a9a681a1dad627da22d4b89cdd/p1-walking-skeleton/evidence/lima/AT10.json)

运维负责人按交互 API、后台短任务、长任务、模型和外部执行资源分别建立负载画像。记录请求吞吐与 p95/p99、队列等待、各类并发、数据库锁等待、模型用量、CPU/内存/存储和失败恢复耗时。恢复演练记录实测 RPO/RTO；按任务/运行/操作/尝试和构建版本串联授权依据、受理者、真实执行者与结果，核验普通用户、异租户和审计员的允许及拒绝视图。以目标架构的镜像摘要生成 SBOM、复扫并处理制品发现。测试环境、可接受的延迟、恢复和成本目标由负责人根据业务决定，测量前保留未知。

**提交复审的决定**：请独立评审 RB-02 至 RB-05 的权威和并发语义、RB-06 的候选排序与许可边界、RB-07 的恢复策略，以及这些限制能否允许隔离实验。请用户仅在相应阶段确认不能由技术推定的事项：是否接受已交接请求的撤权语义、完整应用的组织/对外使用方式、首个正式 MVP 的人群与价值任务、真实环境与费用上限。
