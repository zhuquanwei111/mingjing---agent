## 拟议方案与可观察验收

1. **跟随 #3 的独立 Draft PR。** 专用分支以 #3 的已核验提交为基线，并暂指向 #3 的分支，使本次差异只含新任务。复用 #3 的检查与恢复能力。备选是以 `main` 为基线，代价是重建或同步开发入口、重复验证，并与 #3 形成交叠。交付前核对两条分支和 PR；依赖有变化时重新评估测试和目标分支。
2. **一个可搬运的版本目录，加一个项目接入。** `engineering-standard/` 持有通用规约、可编辑 Mermaid 图、模板、来源与成熟度说明、一套 Python/Make/GitHub 技术适配和范围明确的技能。仓库根只补入口，明镜的技术、阶段、环境与实测在 `docs/` 项目页。候选版本由 Git 提交、目录版本和变更记录定位，复用时可窄范围复制包并固定来源提交。
3. **复用检查与回流。** 复用现有文档链接、工作区状态和 GitHub 检查入口。扩展包文件的链接覆盖，并检查可发现的技能入口。针对坏链接、越界路径或错配入口运行反例。普通小改动保持轻量，独立方案评审用于实质取舍，独立代码审查用于候选变更。两者均由原 Agent 收取结果。
4. **实测后交付。** 在 Mac 用一个新会话从根规则与本文件恢复任务，实际执行下一条安全验证命令。按装载结果核验本机 Codex 项目设置及技能发现，保留桌面会话的实际差异。检查当前 Space 文档及可用只读能力，再确定 Git 与 Space 的权威边界。提交候选、独立审查、处理反馈后创建 Draft PR，确认对应 GitHub ARM64 run 和完整日志。

### 方案评审执行入口的新增设计

拟在项目决定需要独立方案评审的任务中，使用一次显式的实施入口进入实现阶段。入口自动调用现有 ChatGPT 登录的原生 Codex，启动全新只读、临时 reviewer，传入正式任务记录和本地 Git 基线，使用结构化结论；审查结果返回原设计 Agent。原设计 Agent 修订后重新进入同一入口，使用新的独立审查。主会话仍处理进度和交付。

触发方式比较了项目内工具钩子和一次命令入口。OpenAI 官方 Hooks 说明，工具钩子出错、超时或返回畸形内容时可继续执行，覆盖也受客户端和工具路径影响。选择直接把后续命令置于本地流程入口的成功分支，按真实退出状态阻断该入口。支持普通小改动沿用已有流程；项目约定明确何时使用方案关卡。GitHub CI 继续承担正式候选验收，项目不引入外部模型 API、GitHub 密钥或生产权限。

补充验收包括真实 reviewer 自动返回需修订、后续命令未启动、实施者更新计划、新 reviewer 独立通过并真正执行后续步骤。另覆盖工具失败、无结论、超时及期间候选变化。第一版部署和回退不改项目权限、远端规则集或已有评审流程。

### 方案关卡设计复核

新增关卡由第二个新只读会话核对，提出三项实施条件。固定 Git 已提交文件和本次计划副本，拒绝其它未提交文件作为隐含依据；实际启动只读、不许提权的 reviewer，仅按显式调用者参数启动实施；一次运行只接收一份有效结果，非零、超时、取消、评审发现或候选变化均阻断。原设计 Agent 已采纳并实现这些条件。自动评审、反馈和修订后的真实链路是下一阶段单独的验收。

补充验收采用原生子代理优先、实际权限和回执合格后使用的原则。独立只读 CLI 可直接回流，人工启动和转交是有证据的后备方式。各端实测分开登记，低风险改动保持轻量。
