## 目标与范围约束

目标是参考资深开发者与权威团队实际采用的机制，结合明镜项目和现有环境，形成完整、可用且可验证的 Codex 开发方式。R1–R4 是最初四项体验需求，不是总任务的全部范围。

- 固定跟踪下表 C01–C09。每次阶段汇报保留九项的状态，不能只汇报当批改动后宣布整体完成。
- 已满足的领域保留现有实现并给出证据；存在缺口才改进。完整覆盖不等于九项都必须新增工具、技能、脚本或长文档。
- 优先批次、复杂度和工期不能自动成为删项理由。需改变目标、降低验收或将适用事项移出本任务时，记录原因并取得用户的明确范围决定；普通实现选择与既有授权内的推进不反复请示。
- 每项区分：上游实际采用的机制、明镜的适配方式、明镜实际验证的结果。上游使用过不等于明镜已经验证。
- 使用图形界面发任务和看结果；Agent 执行必要命令。用户可自愿用终端复核，保留人工合并决定。不得把自动合并、全天守护、安装完整技能库或额外付费服务追加为完成条件。

本轮 P2 开发中，用户明确确认：R2 没有提交提醒；R3 的 PR 已实际创建和持续更新；R4 没有人工搬运评审意见。用户自愿使用 `gh` 查看 PR 状态并人工合并，这不是流程缺陷。

R1 仍需落实并验证任务结束提示和可恢复接续；当前是未完成验证，不是已证明无法解决。不能把固定 token 比例、发生压缩或两次失败直接设为强制换会话条件。

## 记录方式与整体完成条件

状态使用“待处理／处理中／待验证／已验证并保留／已验证并改进／不适用（附理由）／外部阻塞”。“不适用”只用于确实超出本项目需求的实现路径，不能用来取消已接受的目标；外部阻塞和待核实都不能算完成。

每项更新只保存必要内容：改变或保留了什么、为什么、实现位置、验证对应的提交与环境、实际结果、剩余事项。引用现有 PR、CI 和报告，不复制完整聊天、运行日志或 reviewer transcript。对不需要代码修改的审查项，记录核对结论与依据。

整体完成必须同时满足：

1. C01–C09 全部有明确结论和相应证据；没有被隐去的适用缺口、待验证或外部阻塞。某项暂时不能完成时，报告真实阻塞，不宣布整体完成。
2. R1 的任务收尾与接续经过实际验证；R2–R4 本轮已通过结论被保留，后续变更没有破坏既有使用方式。
3. 当前实现、项目入口、检查范围和实际生效的合并条件一致；当前提交的验证与历史记录清楚分开。
4. 新增配置或机制已做适用的独立审查和实际验证；纯文档、配置、运行时代码按影响选择检查，不机械重复全部本地测试。
5. 最终报告逐项覆盖九个领域，说明保留、修改、不适用及限制；不能用“首批完成”“CI 已绿”或“已合并 PR”替代总任务验收。
