# 09 待核验事项与决策条件

## 当前未知
- 实际开发技术栈、团队规模、部署拓扑和运维能力。
- 首期是否确实需要跨天等待与强持久化恢复。
- 真实负载、预算、数据驻留与外部模型使用政策。
- 对象存储现有资产及候选的许可证、维护和 S3 兼容性。
- 现有身份系统是否可复用，是否需要 SpiceDB 级关系授权。
- 是否确实需要不可信代码执行、复杂多模型路由或知识运营后台。

## 关键技术验证
1. temporalio-langgraph 1.0.0 与目标 Temporal Server/Python SDK/LangGraph 组合是否实际兼容。
2. 插件 Graph API/Functional API、execute_in、interrupt、Store 限制、streaming 和恢复粒度。
3. 活动重试、审批撤权、取消、预算与业务收据是否能在统一边界协作。
4. 旧任务跨 Worker/能力版本升级时是否可继续或明确迁移。
5. 是否有必须侵入上游核心的改动。
6. 各候选组件的实际生产使用证据与推荐版本/发行形态是否对应。

## 不应直接采信的调研说法
- “Temporal 自动保证业务写恰好一次”。
- “所有组件均为无附加条件 MIT”。
- “自建公共层只需固定几百或几千行代码”。
- “LangGraph 无持久化与中断恢复能力”。
- “官方集成已 GA 因而明镜组合已生产验证”。
- “SpiceDB 权限示例代码已通过安全审查”。
- “Kill-switch 可以自动撤销所有已发生动作”。
- “开源框架库等于完整可部署应用”。

## 需要重新决策的情况
- 官方插件的恢复或状态语义无法满足关键要求。
- 为接入异构能力必须大幅改写运行核心。
- Temporal 自托管运维成本不适合现实团队。
- 关键许可、数据出口或依赖出现无法接受的限制。
- 首期没有长任务需求，轻量 Agent SDK + 自有服务更经济。

备选先评估 Temporal + Pydantic AI；若顶层引擎本身不适合，再比较 Dapr + Dapr Agents。不要因业务幂等逻辑错误直接换引擎。
