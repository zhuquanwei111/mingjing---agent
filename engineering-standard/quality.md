# 代码、测试、审查与交付

## 实现与架构

- 沿用实质上可复用的入口、类型和模块。按稳定契约组织代码，保留被支持的接口、持久数据和错误语义。必要的兼容变更写出迁移与回滚。代码应可读、职责清晰，依赖方向可从源文件与架构图核对。
- 外部 I/O、认证、存储和不可逆副作用集中在可观测边界。需要重试、取消、并发或恢复时，明确可重复步骤、状态所有权、操作结果不明的处置和数据一致性。用真实入口验证这些行为。
- 对明确且经常被破坏的边界，先看既有测试、静态检查或可复用的工具。确定性检查由本地与 CI 共用命令。新增检查应指出失败位置、传播非零状态，并有能触发失败的例子。
- 随行为更新消费者需要的示例、接口、运行和决策文档。公共契约或安全边界有改动时，要能从 PR 找到相关实现、文档与验证。

## 选择能证明目标的测试

| 层次 | 用来验证 | 适用例 |
| --- | --- | --- |
| 快速静态检查 | 格式、语法、类型、导入约束、文档引用 | 采用项目已有检查并记录其覆盖范围 |
| 单元或组件 | 规则、错误路径、边界值和可导致回归的代码路径 | 修复前证实一条相关反例失败，修复后复验 |
| 契约与集成 | 公开入口、服务依赖、迁移、权限、失败与一致性 | 用合成数据，运行适用的真实依赖及旧数据样本 |
| 端到端或目标环境验收 | 关键用户路径、部署目标、故障后恢复与清理 | 核实目标系统/架构、实际候选、作业日志及结果 |
| 安全、负载等专项 | 对应风险、已授权的边界和量化目标 | 记录规模、限制、工具版本、可重现结果和未覆盖项 |

由影响范围选择最小充分测试和项目要求的必需检查。CI 在干净环境运行同一入口、固定依赖并记录版本，快速检查先给反馈。测试失败保留原结果并诊断。测试不稳定时查明原因，使用有理由、有上限的重试，保留重试前后的结果。任何隔离或变更门禁的决定都应有显式责任人和修复安排。

每项证据记录 `候选或 diff + 环境/架构 + 命令或作业 + 退出状态 + 日志链接`。有失败、跳过或阻断时分别标明。PR 事件可能测试临时合并提交，记录 PR head 和实际 checkout SHA；基线更新后复核证据对新候选仍适用。

## 独立代码审查和反馈

1. 固定基准和候选，先跑聚焦检查。由原实施者发起一个独立只读 reviewer。提供需求、权威项目规则、基准和候选以及验证范围。让评审者直接阅读完整差异与相关调用方。
2. 按可行动性排序，检查设计与已支持行为、正确性、复杂度、验证、文档、安全和发布影响。发现包含位置、条件、影响、证据和建议。审查者提供意见和剩余不确定性。
3. 原实施者读取并核实意见，修复成立的问题或记录理由，运行受影响检查并复审改变审查结论的候选。重要或争议取舍由维护者决策。缺少有效结果时记为审查未完成。
4. 在任务或 PR 记录评审对象、发现、处置和复验。原实施者持续处理，用户可以直接审核最终建议及证据。

## 提交、PR 与合并

- 在任务分支只暂存本任务文件，检查暂存差异和不应公开的材料。小型、连贯提交说明原因。保留其他工作的改动和分支。
- 有 GitHub 写入授权时推送专用分支、创建或更新同一 PR。使用 [PR 模板](templates/pull-request.md)记录目标、变化、已做的验证、审查处置、回滚及仍待决策。草稿适用于依赖未合并、仍在验证或由用户审阅的任务。
- 核实服务器实际启用的规则、目标分支及必需检查来源。适用 CI 以当前候选为准。对已取得的失败和评审反馈在同一任务处理，确有阻断时记明证据。
- 用户或指定维护者验收并决定合并。跑测试、写入分支、创建 PR、合并、发布和部署分别遵守其授权及门禁。连续集成以小批量和快速反馈减小集成风险。长期任务持续从目标分支复核依赖，合并策略由项目指定。
