# 补充事前判据 · 活着的不同执行器接管

既有 f35d5a6 独立完成的六例使用稳定执行器 ID 的新 PID。运营问题是另一台已经在线、使用不同 executor_id 的开源 DBOS 3.6.0 进程能否接手。新增两个隔离样本，均用此前锁和收端，关闭 Conductor。不改变原六例判据。

1. 第一代执行器 A 真实提交意图、202 后在同一未完成 step 内暂停。不同 ID 的 B 在故障前已经 launch 并报告就绪，B 不主动扫描或恢复。收端打开后台作业，确认发送/效果/费/模型/交付=1/1/1/1/0，动作结果空。控制器 SIGKILL A，确认 exit=-9。从确认旧进程死亡后连续观察至少 8 秒，采样两端事实及引擎归属，记录是否发生无显式介入的接管。只宣称这个时间窗和配置的观测。若有自动接管，原样报告，不能将它归入后续显式恢复。
2. 然后向同一个已在线 B 发送仅用于实验编排的信号，使 B 调用公开的 DBOS.recover_workflows([A的ID])，记录返回 ID、前后真实引擎归属、两 PID、同一未完成步骤和同一工具 operation/call。合格为原 workflow 在 B 结束且接回初始 SDK 会话；工具发送/效果/模拟收费仍为 1/1/1，模型2、交付1。若在观测窗内已自行接管，则另外记录显式调用是否无操作及终值，不把自动、显式路径混淆。
3. 加入错误故障判断负对照：在独立裸步骤样本中保留 A 存活且仍暂停在同一已接收未提交 step，B 显式恢复 A。若观察到第二次发送/一个效果/两笔费，记录并证明故障探测与外部发送幂等仍是自托管责任；若 DBOS 拒绝或自然防重，如实保留。在记账后再次核两 PID 活跃。该样本不连接付费或生产系统。

收端原始行、PG 里的 DBOS 状态、时间窗口/实际采样时刻、进程存活与提交/返回 ID 都归档。此试验不测生产集群失联判定、脑裂策略或运维工时；不能据此声称双活免费故障探测已经具备。参考固定上游 [recover_workflows](https://github.com/dbos-inc/dbos-transact-py/blob/2cf279cf380152b426ecd451d573ccc41f5715a6/dbos/_dbos.py) 及[官方恢复说明](https://docs.dbos.dev/production/workflow-recovery)。
