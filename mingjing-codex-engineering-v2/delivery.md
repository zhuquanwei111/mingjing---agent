# 开发顺序与验收

本包启动第一项正式代码开发。下表保留完整产品的演进方向，按可单独验收的增量组织，不预定工期、并发数字、行业功能或上线日期。每批次在任务账把具体需求映射到正式源码、用例、提交与 CI；实验 V01–V06 只提供可复用的测试条件。

| 顺序与交付 | 需求、依赖和正常路径 | 必过的反例与可观察结果 |
| --- | --- | --- |
| 1．提交或交付前的质量判定 | FR-24、36、38 的判定部分，AC-15 的库级断言。调用方提供固定任务/规则版本、非空必需项和可信校验器产生的逐项证据。返回可交给下一道门的结果、缺项及原因。 | 工具成功但缺项、证据不匹配、结论冲突、校验不可用均不能给出就绪。两项均得到当前版本的肯定证据才就绪。判定本身不写业务账，不触发外部动作。下一批在实际交付端核对零次发送。 |
| 2．宿主受理与第一条受控直接调用 | FR-01、10–15、21、24–26、32–33、35、38、41；AC-01、02、06、15。先接可信身份，固定能力版本、Task/Run、权限和资源范围，真实 PostgreSQL 保存请求与业务收据，执行后接第一项判定。 | 无权、跨租户、未发布、重复键冲突、版本和证据错误。以产品状态、同一操作的独立收据数及交付端接收数核对；未满足条件时正式交付数为零。 |
| 3．持久工作流、恢复和取消 | FR-07–09、25–31、37、39–40；AC-03、05、08、11、13、14、16。使用 Temporal，按业务稳定操作号先登记派发，再做实际 I/O，接共享预算。 | 提交成功后丢回执、Worker 死亡、暂停和连续运行时撤权、父项取消后迟到回调。用真实数据库和服务验证单次副作用、未知态保留额度、子项不超总额、已取消下游零次派发。 |
| 4．原生 Agent、上下文与未知能力 | FR-02–06、09–20、32–34、39、41；AC-04、05、07、13、17。Pydantic AI 接受允许的工具子集，模型网关验证兼容；模型和固定工作流共用已授权能力。 | 两工具形成多轮回传，切换或撤回模型能力、旧上下文失权、无进展和更换新能力签名。用可控模型与获准真实模型分别留证，并实测模型轮次中途崩溃的恢复粒度。 |
| 5．知识、产物、评测与投产治理 | FR-16–24、32–41；AC-09、10、12，并回归 AC-01–17。区分业务事实查询与获准资料 RAG，版本化资料和产物引用；数据准入、发布、撤回、评测数据与真实审计独立治理。长期记忆按需启用。 | 撤回、过期、错引、跨租户、错误降级、质量规则升级和并发资源争用；可从受控关联标识重建事实。按目标负载测试、备份重建、灰度回退后，另外决定相应能力的真实流量准入。 |

完整非功能验收涵盖可靠性、安全性、一致性、隔离性（NFR-01–03、05），以接收端、故障注入和事务状态证明；性能与成本（NFR-04、10）按交互/后台/模型/外部资源分别测量；可维护、可扩展、可观测、可测试、可部署与恢复（NFR-06–09、11）以版本回退、未知能力接入、端到端追踪、固定数据集回归、备份恢复演练验证。实际身份系统、数据保留、时延/可用性、预算阈值与拟用模型由适用阶段实测确认。

## 第一项的接口和测试

Python 调用边界要求传入任务标识、规则版本、必需项，以及从可信业务适配器取得的逐项验证记录。每条记录绑定任务、规则版本、要求项、证据引用和肯定/否定/待核结论。调用者另行说明本次验证是否可用。公开返回记录按任务契约的必需项顺序列出结果，并给出就绪状态和可解释的原因；不返回底层资料。对已经校验的同一证据重复上报应保持相同结论。不得依据最后一条记录覆盖矛盾结论。空契约、含糊身份或无效枚举应显式拒绝或待核。未知要求项和错误绑定不能补足缺项。

该接口面向可信的宿主/Worker 应用代码；证据来源验证、当前授权和两步交付之间的并发控制由下一批真实适配器负责。模型输出、HTTP 请求正文和任意外部字典不能直接作为可信证据交给此边界。此批使用 Python 标准库与 unittest，独立源码目录，运行时不导入旧 core。正式门禁沿原 ARM64 作业增加对应新代码测试；原回归继续执行。正式 API、服务凭据、模型额度、数据库迁移与部署均在相应阶段接入。
